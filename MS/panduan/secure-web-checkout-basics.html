Membina Checkout Web Lebih Selamat: Validasi, Secrets dan Webhook

KasuhaNET Resources · Panduan teknikal · Dikemas kini 12 November 2026

Halaman checkout tidak menjadi selamat hanya kerana butangnya tersembunyi atau borangnya kelihatan kemas. Server perlu membuat keputusan penting: produk yang sah, harga sebenar dan sama ada pembayaran benar-benar selesai.

1. Anggap input pelayar sebagai data tidak dipercayai

Pelawat boleh mengubah HTML, JavaScript dan permintaan rangkaian. Jangan menerima harga, diskaun atau status pembayaran yang dihantar oleh pelayar sebagai sumber kebenaran. Pelayar sepatutnya menghantar ID produk dan butiran pelanggan; server perlu mendapatkan produk daripada senarai yang ditetapkan.

2. Sahkan data pada server

Semak sama ada produk yang dipilih wujud, medan wajib diisi, alamat e-mel munasabah dan panjang input berada dalam had yang sesuai. Lakukan validasi sekali lagi pada server walaupun pelayar menggunakan required atau jenis input e-mel.

3. Simpan kunci rahsia pada server

Kunci rahsia penyedia pembayaran perlu disimpan dalam tetapan secret terenkripsi atau pemboleh ubah persekitaran platform hosting. Jangan letakkannya dalam JavaScript awam, HTML, fail konfigurasi yang dikomit atau permintaan dari bahagian pelanggan. Jika kunci terdedah, gantikannya melalui dashboard penyedia.

4. Cipta sesi pembayaran pada server

Server perlu membina sesi checkout menggunakan harga produk yang dipercayai dan memulangkan URL checkout penyedia atau respons selamat kepada pelayar. Gunakan HTTPS dan sahkan permintaan datang daripada origin yang dibenarkan, sambil memahami bahawa semakan origin bukan pengganti kepada pengesahan pengguna atau had kadar permintaan.

5. Sahkan pembayaran melalui webhook yang disahkan

Pelanggan kembali ke halaman berjaya bukan bukti pembayaran telah berjaya. Gunakan mekanisme webhook bertandatangan penyedia, sahkan tandatangan berdasarkan badan permintaan asal seperti yang didokumenkan oleh penyedia, dan kemas kini pesanan hanya selepas peristiwa pembayaran yang sah disahkan.

6. Jadikan pemprosesan webhook selamat untuk percubaan semula

Penyedia pembayaran mungkin menghantar semula webhook. Simpan ID peristiwa penyedia atau gunakan kaedah idempotent supaya peristiwa sama tidak memenuhi pesanan dua kali. Semak ID pesanan, jumlah, mata wang dan status pembayaran sebelum mengubah status pemenuhan.

7. Lindungi data pelanggan

  • Kumpul maklumat yang benar-benar diperlukan untuk melengkapkan pesanan.
  • Jangan log kunci rahsia, butiran penuh kad atau maklumat peribadi yang tidak diperlukan.
  • Gunakan pertanyaan pangkalan data berparameter, bukan membina SQL daripada input pengguna.
  • Hadkan akses kepada rekod pesanan dan kemas kini dependency.
  • Sediakan maklumat privasi, pemulangan wang dan sokongan yang jelas sebelum pembelian.
Sebelum pelancaran

Uji senario pembayaran berjaya, dibatalkan, ditolak dan webhook berulang dalam persekitaran ujian penyedia. Pastikan pesanan tidak boleh ditandakan sebagai telah dibayar hanya dengan mengubah URL atau permintaan pelayar.

Artikel ini menerangkan amalan kejuruteraan umum, bukannya pensijilan atau audit keselamatan. Ikuti dokumentasi integrasi terkini penyedia pembayaran dan uji pelaksanaan anda sendiri.
