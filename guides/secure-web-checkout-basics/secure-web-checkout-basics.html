Building a Safer Web Checkout: Validation, Secrets and Webhooks

A checkout page is not secure merely because its button is hidden or its form looks polished. The server must make the important decisions: which product is valid, what it costs and whether payment has actually completed.

Core rule

A checkout is not secure just because the page uses HTTPS or the payment button looks correct. Treat the browser as untrusted, keep payment decisions on the server and fulfil an order only after the payment provider has been verified.

1. Treat browser input as untrusted

Visitors can edit HTML, JavaScript, form fields and network requests. Never accept a client-supplied price, subtotal, discount amount, tax amount, currency or payment status as authoritative. The browser should submit product identifiers, quantities and the minimum customer details needed for the order. The server must retrieve current prices and product availability from trusted records and calculate the total itself.

Validate quantities as positive integers, reject unknown product identifiers, enforce reasonable limits and re-check coupon eligibility on the server. A hidden field, disabled button or read-only input is still controlled by the visitor.

2. Validate data on the server

Browser validation improves usability, but it can be bypassed. Repeat validation on the server for required fields, email format, phone format where needed, input length, allowed values and quantity limits. Normalise data consistently and reject unexpected fields rather than silently trusting them.

Use parameterised database queries for values from forms. Apply rate limits to checkout creation and other sensitive endpoints to reduce automated abuse. Do not rely on a CAPTCHA as the only protection.

3. Keep secret keys out of public code

Payment-provider secret keys and webhook signing secrets belong in the hosting platform's encrypted secret settings or a dedicated secrets manager. Never place them in browser JavaScript, HTML, public environment variables, screenshots or a committed configuration file. Restrict access to the smallest set of services and people that need it.

If a key is exposed, revoke or rotate it through the provider dashboard, check recent activity and update the server configuration. Removing the key from the latest commit alone does not make an exposed key safe again.

4. Create the payment session on the server

The server should create the payment session using the trusted product price, expected currency and a unique order reference. Return only the provider-hosted checkout URL or the minimum safe response needed by the browser. Where possible, use the provider's hosted checkout so your application does not directly collect or process card numbers or card security codes.

Use HTTPS for the whole checkout journey. Validate the request's origin where appropriate, protect browser-initiated state-changing requests against CSRF, and use authentication or a short-lived order token where the order flow requires it. Origin checks alone are not authentication and do not replace server-side validation or rate limiting.

5. Do not trust the return or success page

A customer reaching a success URL does not prove that money was received. Query parameters, browser redirects and client-side messages can be changed or replayed. Keep the order in a pending state until the provider's authenticated server-to-server notification or a server-side status check confirms the payment.

Before marking an order paid, match the provider account, order reference, amount, currency and final payment status against the values stored for that order. Handle failed, cancelled, pending, expired, refunded and disputed states separately. A successful authorisation is not always the same as a captured or settled payment; follow the provider's documented status model.

6. Verify webhook signatures correctly

Use the payment provider's official verification library or documented verification procedure. Verify the signature using the exact raw request body and headers required by that provider before trusting the event. Parsing and re-serialising JSON first can change the bytes and cause verification to fail. Never invent your own signature format or accept an unsigned callback as proof of payment.

Accept webhook traffic over HTTPS, validate the expected HTTP method and payload format, and reject missing or invalid signatures. Keep the signing secret private. The webhook route may need a narrowly scoped CSRF exemption because the provider cannot submit your browser's CSRF token, but signature verification must be enforced before the route is trusted.

7. Make webhook handling idempotent

Providers retry deliveries, and events may arrive more than once or out of order. Store each verified event identifier and make order fulfilment idempotent so the same event cannot trigger duplicate delivery, account credit or email actions. Use a database uniqueness constraint or an equivalent atomic check rather than relying only on an in-memory flag.

Do not assume events arrive in sequence. When an event may be stale or ambiguous, retrieve the current payment or order state from the provider before changing fulfilment. Acknowledge an authenticated duplicate without repeating its side effects, and only return success after the event has been durably recorded or queued.

8. Protect customer and payment data

  • Collect only the personal information required to complete and support the order.
  • Prefer provider-hosted payment pages so card data does not pass through your application.
  • Never store card security codes or log full card details, secret keys, signing secrets or full webhook payloads.
  • Restrict access to order records and define appropriate retention and deletion practices.
  • Keep dependencies and server software updated, and use parameterised SQL queries.
  • Publish clear privacy, refund, delivery and support information before purchase.

9. Monitor failures without leaking secrets

Record useful operational details such as order reference, provider event ID, event type, processing result and timestamp. Redact credentials, signature headers and unnecessary personal data. Monitor repeated signature failures, unexpected paid-state changes, duplicate events and unusual checkout request volume. Return generic error messages to visitors and keep detailed diagnostics in access-controlled logs.

Pre-launch security tests
  • Change the price or quantity in a browser request and confirm the server recalculates the total.
  • Open or refresh the success URL without paying and confirm the order stays unpaid.
  • Send a webhook with a missing or invalid signature and confirm it is rejected.
  • Deliver the same valid event twice and confirm fulfilment happens once.
  • Test declined, cancelled, pending, refunded and delayed payment notifications.
  • Confirm logs and error responses do not expose keys or customer payment data.

This guide covers general security principles, not a payment-provider certification or a formal security audit. Payment providers use different event formats and status rules. Follow the current documentation for the provider you actually use and test the complete order lifecycle before launch.
