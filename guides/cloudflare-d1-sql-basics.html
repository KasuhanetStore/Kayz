Cloudflare D1: Inspect Tables and Run Safe SQL Queries

KasuhaNET Resources · Technical guide · Updated 12 November 2026

Cloudflare D1 is a serverless SQL database built on SQLite. The first step when maintaining an existing project is to inspect its schema and understand the data before changing anything.

Important

Use the database name shown in your Cloudflare configuration or dashboard. A Worker binding name such as DB is a code-level variable and is not necessarily the actual D1 database name.

1. List available D1 databases

With Wrangler installed and authenticated to the correct Cloudflare account, run:

npx wrangler d1 list

Identify the database used by the project. Check the project's Wrangler configuration and deployment environment before running remote commands.

2. Inspect the table list

Replace YOUR_DATABASE_NAME with the exact database name returned by the previous command:

npx wrangler d1 execute YOUR_DATABASE_NAME --remote --command "SELECT name FROM sqlite_master WHERE type = 'table' ORDER BY name;"

This query reads SQLite's schema metadata and lists tables. It does not modify records.

3. Inspect a table's columns

npx wrangler d1 execute YOUR_DATABASE_NAME --remote --command "PRAGMA table_info('stripe_orders');"

Replace stripe_orders with the table you want to inspect. The result describes column names, types, nullability, default values and primary-key information.

4. Read a small sample

npx wrangler d1 execute YOUR_DATABASE_NAME --remote --command "SELECT id, status, created_at FROM stripe_orders ORDER BY created_at DESC LIMIT 10;"

Select only the columns you need and use a small limit. Avoid printing customer names, email addresses, phone numbers or other personal data into public logs or screenshots.

5. Use parameterised queries in Workers

When application input is involved, bind values instead of concatenating them into SQL strings:

const result = await env.DB.prepare(
  "SELECT id, status FROM stripe_orders WHERE id = ?"
).bind(orderId).first();

Parameter binding helps prevent SQL injection and keeps data values separate from SQL syntax. Table and column names generally cannot be supplied as ordinary bound values; choose those from trusted, fixed application logic.

6. Back up and change schema carefully

Before a migration or destructive query, confirm the target database and environment, create a backup using the current Cloudflare-supported workflow, and test the migration against a non-production copy when possible. Review every UPDATE or DELETE with a matching WHERE clause. Never run a destructive statement just to discover what it does.

Useful checks

  • Confirm the correct Cloudflare account and database before using --remote.
  • Keep production and development database names clearly distinguished.
  • Use migrations tracked in version control for repeatable schema changes.
  • Keep database credentials and API tokens out of source files.

Refer to Cloudflare's current D1 and Wrangler documentation for version-specific commands and backup procedures.
