Cloudflare D1: Inspect Tables and Run Safe SQL Queries

Cloudflare D1 is a serverless SQL database built on SQLite. The first step when maintaining an existing project is to inspect its schema and understand the data before changing anything.

Before you run commands

Use the database name shown in your Cloudflare configuration or dashboard. A Worker binding such as DB is a code-level variable, not necessarily the D1 database name. Commands marked --remote act on a remote database, so confirm the account, database and environment first.

1. List your D1 databases

With Wrangler installed and authenticated to the intended Cloudflare account, list the available databases:

npx wrangler d1 list

Match the database to the project's Wrangler configuration. Check the database name, database ID, binding and environment rather than choosing one based on a similar name.

2. List tables without changing data

Replace YOUR_DATABASE_NAME with the exact database name:

npx wrangler d1 execute YOUR_DATABASE_NAME --remote --command "SELECT name FROM sqlite_schema WHERE type = 'table' ORDER BY name;"

This reads SQLite schema metadata. It does not insert, update or delete application records. D1 may expose internal system objects in schema listings; do not treat undocumented internal tables as application tables or attempt to modify them.

3. Inspect a table's columns

npx wrangler d1 execute YOUR_DATABASE_NAME --remote --command "PRAGMA table_info('stripe_orders');"

Replace stripe_orders with the table you need to inspect. The output includes column names, declared types, whether NULL is allowed, default values and primary-key position. It describes the schema, not the actual customer data.

4. Read a limited sample

npx wrangler d1 execute YOUR_DATABASE_NAME --remote --command "SELECT id, status, created_at FROM stripe_orders ORDER BY created_at DESC LIMIT 10;"

This is an example only. Use column names that really exist in your table, and keep the result set small. Select only what is needed. Avoid exposing names, email addresses, phone numbers, payment details or other personal information in logs, screenshots or support messages.

5. Use parameterised queries in a Worker

When a query uses application input, bind values instead of joining them into an SQL string:

const order = await env.DB.prepare(
  "SELECT id, status FROM stripe_orders WHERE id = ?"
).bind(orderId).first();

first() returns the first matching row, or null when no row matches. For multiple rows, use all(); for statements that change data, use run() and inspect the result. Parameter binding helps prevent SQL injection by keeping values separate from SQL syntax. It does not make arbitrary SQL fragments safe: table names, column names and sort directions should come from trusted, fixed application logic.

6. Check database integrity

SQLite's quick check can help identify structural problems:

npx wrangler d1 execute YOUR_DATABASE_NAME --remote --command "PRAGMA quick_check;"

A result of ok means the check did not report a structural issue. It is not a substitute for checking whether application data is complete, correct or consistent with business rules.

7. Export a backup before risky changes

Wrangler can export a remote D1 database to a SQL file:

npx wrangler d1 export YOUR_DATABASE_NAME --remote --output=./d1-backup.sql

Store the export in a private, access-controlled location. A full export can contain personal and business data, so do not commit it to a public repository or attach it to a public support request. Confirm that the export completed and that the file is protected before proceeding.

8. Make schema changes through migrations

For a maintained project, keep schema changes as version-controlled migration files and test them against a local or preview database before production. Wrangler provides migration commands such as:

npx wrangler d1 migrations list YOUR_DATABASE_NAME
npx wrangler d1 migrations apply YOUR_DATABASE_NAME --local

Only apply migrations to the remote production database after reviewing the exact changes and testing the migration path. Cloudflare's migration workflow captures a backup when migrations are applied, but this does not remove the need to verify the target environment and keep an independent export when appropriate.

9. Review destructive SQL carefully

Before running UPDATE or DELETE, first run a matching SELECT with the same WHERE condition to confirm which rows will be affected. Check the affected-row result after the change. Never run DROP TABLE, an unrestricted DELETE or a broad UPDATE just to discover what it does.

Practical safety checklist

  • Confirm the Cloudflare account, database name and environment before every remote command.
  • Keep development, preview and production databases clearly distinguished.
  • Use prepared statements for values received from users or other untrusted sources.
  • Keep API tokens, database exports and customer records out of public source control.
  • Use reviewed migrations for repeatable schema changes and retain protected backups.
  • Limit database access to the people and services that need it.
