Building a Safer Web Checkout: Validation, Secrets and Webhooks

KasuhaNET Resources · Technical guide · Updated 12 November 2026

A checkout page is not secure merely because its button is hidden or its form looks polished. The server must make the important decisions: which product is valid, what it costs and whether payment has actually completed.

1. Treat browser input as untrusted

A visitor can edit HTML, JavaScript and network requests. Do not accept a price, discount or payment status sent by the browser as authoritative. The browser should submit a product identifier and customer details; the server should look up the product from a fixed allowlist.

2. Validate data on the server

Check that the selected product exists, required fields are present, email addresses are plausible and input lengths are within reasonable limits. Apply validation again on the server even if the browser uses required or an email input type.

3. Keep secret keys on the server

Payment-provider secret keys belong in the hosting platform's encrypted secret or environment-variable settings. Never place them in public JavaScript, HTML, a committed configuration file or a client-side request. If a key is exposed, rotate it in the provider dashboard.

4. Create the payment session on the server

The server should construct the checkout session using the trusted product price and return only the provider's checkout URL or a safe response to the browser. Use HTTPS and verify that the request is coming from an allowed origin, while remembering that origin checks are not a replacement for authentication or rate limiting.

5. Confirm payment with a verified webhook

A customer returning to a success page does not prove that a payment succeeded. Use the provider's signed webhook mechanism, verify the signature against the raw request body as documented by the provider, and update the order only after a valid payment event is confirmed.

6. Make webhook processing safe to retry

Payment providers may retry webhook deliveries. Store the provider event identifier or otherwise make processing idempotent so the same event cannot fulfil an order twice. Check the order identifier, amount, currency and payment status before changing fulfilment state.

7. Protect customer data

  • Collect only the information needed to complete the order.
  • Do not log secret keys, full card details or unnecessary personal information.
  • Use parameterised database queries rather than building SQL from user input.
  • Restrict access to order records and keep dependencies updated.
  • Provide clear privacy, refund and support information before purchase.
Before launch

Test successful, cancelled, declined and repeated webhook scenarios in the provider's test environment. Confirm that an order cannot be marked paid solely by changing a URL or browser request.

This article describes general engineering practices, not a certification or security audit. Follow the payment provider's current integration documentation and test your own implementation.
